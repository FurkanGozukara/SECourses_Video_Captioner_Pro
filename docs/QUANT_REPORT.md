## Decisions and Micro-benchmarks

- INT4 uses one FP32 scale per output row. On six TimeChat layers, row scales measured 12.3432% relative L2 error versus 10.6098% for group-128 scales (1.35345x MSE). The modest accuracy win did not justify K-split accumulation or a second lossy re-quantization step, so the row layout keeps one INT8 GEMM and one output-channel epilogue.
- Decode selects a kernel once per GPU, scheme, dtype, and shape, then caches it in `vcap/models/quant/.kernel_cache.json`. For a real TimeChat M=1, K=N=3584 projection, INT8 measured 0.3019 ms with padded `_int_mm`, 0.0694 ms with BF16 dequantization, and 0.0337 ms with the fused Triton GEMV. INT4 measured 0.6409 ms, 0.9424 ms, and 0.0345 ms respectively. Triton was selected for both.
- Qwen3 expert dispatch sorts assignments, copies one compact `(expert, count)` table to the host, runs only active experts, and scatter-adds route-weighted results. For one token with 8/128 experts, INT4 measured 1.507 ms versus 2.927 ms for the Transformers-style active-expert loop and 10.082 ms for a naive 128-expert loop: 1.94x and 6.69x speedups. INT8 measured 1.506, 2.960, and 10.064 ms: 1.97x and 6.68x. Both comparisons had zero output delta.
- The custom BF16 streaming loader reproduced TimeChat reference logits bit-for-bit. Qwen3 BF16 reference logits used `device_map="auto"` with 26 GiB on GPU and 60 GiB on CPU; its media run was intentionally omitted.
- Qwen3 Instruct INT8 text verification passed, but its 33.02 GB checkpoint leaves no room for the 7,556-token video activations on a 32 GB card. A full-media attempt entered Windows shared-memory paging and was stopped after 20 minutes, so that media row is marked skipped. INT4 completed the official 2,048-token run.

Peak values are PyTorch allocator high-water marks. Under Windows WDDM, allocations can exceed the card's 32 GB of dedicated VRAM by paging into shared system memory; the AVoCaDO and Qwen3 INT4 media peaks above 32 GB indicate paging, not additional physical VRAM.
